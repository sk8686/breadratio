# BreadMath 项目级原则

## 1. 项目定位

BreadMath 不是内容社区、SaaS 平台或课程网站，而是一个长期运行、低维护、零后端成本的烘焙工具站。

项目的核心目标：

- 用真正有用的烘焙计算工具解决用户的实际问题
- 通过自然搜索流量获取稳定访问
- 在未来具备流量后接入 Google AdSense 变现
- 除域名外不引入持续性成本
- 上线后无需依赖持续更新内容来维持价值

## 2. 最高约束

以下约束优先级高于“功能更多”“页面更炫”“短期看起来更完整”。

### 2.1 零持续成本

- 除域名外，不引入任何持续付费项
- 不依赖服务器、数据库、定时任务、付费 API、付费 SaaS
- 默认方案必须能在 GitHub + Cloudflare 免费计划上长期运行

### 2.2 低维护

- 网站上线后应主要依靠工具本身长期产生价值
- 不把持续写文章、频繁更新数据、人工审核内容作为增长前提
- 新功能只有在长期维护成本可接受时才可进入

### 2.3 SEO 优先

- 每个页面都必须对应明确搜索意图
- 页面标题、描述、正文、FAQ、内部链接都要服务于收录和点击
- 不做对搜索引擎不友好的重客户端渲染、登录墙、内容折叠墙

### 2.4 用户价值优先

- 每个工具页必须能独立解决一个真实、具体、可复用的问题
- 不做“看起来丰富但没有明确需求”的功能
- 不做只能服务站长想象、却不能服务真实烘焙用户的问题页

### 2.5 未来广告兼容

- 项目初期不接广告，但所有布局、性能和内容策略都必须为未来接入广告留空间
- 广告不能破坏核心工具体验、加载速度和可读性

## 3. 产品原则

### 3.1 只做常青型页面

优先建设：

- 水合率计算器
- 配方缩放器
- 酵母换算器
- 烘焙百分比计算器
- 披萨面团计算器
- 酸种喂养/目标量计算器

这些页面的共同特点：

- 搜索需求长期存在
- 计算规则相对稳定
- 不需要频繁维护
- 能直接解决操作性问题

### 3.2 每个页面都必须回答 3 个问题

在新增任何页面前，必须先回答：

1. 用户会搜什么词找到它？
2. 它解决的痛点是什么？
3. 它是否能在不增加持续维护成本的前提下长期存在？

如果这 3 个问题回答不清楚，则默认不做。

### 3.3 功能不是越多越好

判断新增功能时，优先看：

- 是否提升核心问题的解决效率
- 是否对应明确搜索需求
- 是否能提高页面质量与转化为回访/收藏

而不是看：

- 是否“看起来更完整”
- 是否“别人网站也有”
- 是否“以后也许能用上”

## 4. 技术原则

### 4.1 默认静态优先

- 优先使用 Astro 静态输出
- 默认不引入后端服务
- 默认不引入用户账号体系
- 默认不采集用户数据

### 4.2 代码结构要服务于长期低维护

- 共享逻辑要抽离，避免英文页和多语言页双份漂移
- 页面脚本中出现重复计算、重复复制逻辑、重复文案处理时，应优先归并
- 不为了“未来可能会用到”过早设计复杂抽象

### 4.3 Cloudflare 免费部署兼容

- 构建产物必须能直接静态部署
- 不依赖 Node 常驻服务
- 不依赖运行时写文件、定时任务或外部状态存储
- 构建和部署流程应适配 GitHub -> Cloudflare Pages

## 5. SEO 原则

### 5.1 页面必须围绕搜索意图组织

每个核心页面都应覆盖：

- 清晰的标题和描述
- 工具本体
- 简明解释
- FAQ
- 相关工具内链

### 5.2 不依赖高频内容运营

- 不以“持续更新博客”作为主要增长方式
- 可以保留少量常青说明内容，但必须和工具页强相关
- 内容的作用是增强页面理解、信任和收录，不是变成另一个需要运营的网站

### 5.3 国际化必须服务于真实搜索，而不是表面多语言

- 只有当页面内容、动态文案、交互提示都达到可用水平时，多语言才算真正成立
- 不能只翻译静态标题，却保留英文交互和英文默认数据

## 6. 广告原则

### 6.1 当前阶段不接广告代码

- 在项目初期不为了广告而牺牲性能、布局稳定性和体验
- 不提前加入会拖慢页面的广告脚本

### 6.2 未来广告接入边界

- 广告必须从属于工具，不得干扰计算流程
- 首屏核心工具区域优先级高于广告位
- 广告布局要避免影响 CLS、可读性和移动端可操作性

## 7. 明确不做

除非未来战略明确变化，否则以下方向默认不做：

- 用户注册/登录
- 配方云存储
- 需要服务端的个性化推荐
- 评论系统
- 论坛/社区
- 依赖人工高频更新的数据页
- 需要持续运营才能成立的专题内容站
- 增加维护复杂度但不明显提升 SEO 或用户价值的炫技功能

## 8. 需求评估清单

以后评估任何新页面、新功能或重构时，必须逐项检查：

- 它是否解决真实痛点？
- 是否存在明确搜索需求？
- 是否保持零持续成本？
- 是否增加后续维护负担？
- 是否兼容 Cloudflare 免费部署？
- 是否会伤害性能、SEO 或可访问性？
- 是否为未来广告接入留下合理空间？

只要有 2 项以上无法通过，就默认不进入开发。

## 9. 当前项目的成功标准

BreadMath 的成功，不是“功能越来越多”，而是：

- 核心工具页稳定可用
- 页面长期可收录
- 用户能快速得到答案
- 维护成本持续很低
- 后续能自然接入广告而不破坏体验

## 10. 执行原则

后续所有开发、修复、重构和新增页面，应遵守以下执行规则：

- 优先修复真正影响用户的问题
- 优先增强真实使用价值
- 优先减少重复代码和多语言漂移
- 优先提高页面可收录性和可理解性
- 不为短期“丰富感”牺牲长期稳定性
